TASK 7 — OTP flow: request / verify / reset password  (3 endpoints)
================================================================================
Overview:
  Forgot-password UI already does 4 steps and only calls fake timers. You build:
    a) POST /auth/request-otp      identify step
    b) POST /auth/verify-otp       OTP step
    c) POST /auth/reset-password   new-password step
  Ek line me: forgot password wala OTP flow (code bhejo -> verify -> password
  reset karo). Dev me code sirf server log me dikhega, email/console.

--------------------------------------------------------------------
a) POST /auth/request-otp
--------------------------------------------------------------------
Body: { "identifier": "ada@example.com" }   // email OR phone

Flow:
  - identifier can be an email or a phone number (frontend already validates).
  - Rate-limit -> @rate_limit(limit=5, window_seconds=300).
  - Generate a 6-digit numeric code. Store HASHED (sha256) in Redis or the
    reset-codes table with:
        key/identifier, code_hash, expires_at = now + 10 minutes, attempts = 0
  - Do NOT reveal whether the account exists (no account -> still "sent").
  - "Send" = log `[OTP] ada@example.com -> 123456` to the server console in dev
    (add SMTP env placeholders for production).
  - Response: 200 { "expires_in": 600 }   // so the UI can count down
  - 429 -> "Too many requests. Please wait a moment." (standard limiter)

--------------------------------------------------------------------
b) POST /auth/verify-otp
--------------------------------------------------------------------
Body: { "identifier": "ada@example.com", "code": "123456" }

Flow:
  - Look up the stored code. If missing/expired/used -> 400
    "That code did not verify. Please try again."   (frontend shows exactly this)
  - Wrong code -> increment attempts; after 5 -> 429
    "Too many attempts. Request a new code." (UI auto-returns to identify)
  - Correct -> mark used + issue a SHORT-LIVED reset JWT:
      jwt payload: { "sub": <user_id or "pending">, "scope": "password_reset",
                     "identifier": email, exp: now + 10 min }
    Frontend does not see this token yet — see TASK 8 (return it in step c).
  - Response: 200 { "verified": true }

--------------------------------------------------------------------
c) POST /auth/reset-password
--------------------------------------------------------------------
Body options:
  Option A (recommended, keeps one round-trip):
    { "identifier": "...", "code": "123456", "new_password": "Str0ng!Pass99" }
    Re-verify code server-side, then set the new password. Simplest, stateless.
  Option B (two-token): { "reset_token": "<jwt>", "new_password": "..." }
    Frontend keeps the JWT from verify-otp in memory and sends it here.

Validation (mirror the register rules):
  new_password: min 8, at least upper + lower + digit + special -> 422
Auth: none (the code/JWT is the credential).
On success:
  - If the account was a pending invite user (hashed_password NULL) ->
    this is how they "register" after invite: SET the password and mark active.
  - Rotate security: invalidate all refresh tokens for this user if you keep
    them in DB (models/refresh_token.py) — optional but recommended.
  - Response: 200 { "detail": "Password updated" }

FRONTEND INTEGRATION: frontend/src/pages/ForgotPassword.tsx — three markers:
  line ~69 : submitIdentifier()  -> await apiFetch('/auth/request-otp', {method:'POST', body: JSON.stringify({ identifier })})  (auth:false not needed)
  line ~286: submitCode()        -> await apiFetch('/auth/verify-otp', {method:'POST', body: JSON.stringify({ identifier, code })})
  line ~414: submitReset()       -> await apiFetch('/auth/reset-password', {method:'POST', body: JSON.stringify({ identifier, code, new_password })})

  (identifiers: the current step copies `identifier` prop into each step; wire
   them through — the FakeStep components already receive the props they need.)
  AFTER wiring the API, ALSO update the OTP "resend" cooldown (30s) if the
  server 429s early, and clear the "Demo build ... placeholder" info toast.

VERIFY: full journey -> identify shows "one-time code" -> type 123456 (from
server log) -> "Set a new password" -> weak rejejede -> strong + match ->
"Password updated" -> then login with the NEW password works.

APPENDIX — CHAT SESSION PERSISTENCE (added with the collapsible history panel)
================================================================================
Frontend now has a per-workspace chat history panel (toggle in the Ask & Chat
header -> slide-in list). Sessions are WORKSPACE-scoped (chats are tied to a
workspace's documents). Today it uses localStorage only (each browser is
isolated). The endpoints below are what a real multi-user backend needs so
history follows the user across devices AND survives backend restarts.

Wire shapes (mirror frontend types):
  Session:  { id, title, workspace_id, created_at, updated_at }
  Message:  { id, session_id, role: "user"|"assistant", content, created_at }
